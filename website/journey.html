The Complete DevOps Journey

This page traces one code change through the entire DevOps pipeline — from code commit to user's browser.

PIPELINE OVERVIEW
Code
→
Build
→
Deploy
→
Monitor
1. Developer writes code locally
A developer edits the React + NestJS source code to add a new feature to TaskFlow. Learn basics
Key Insight: Everything starts with code running in a local environment.
2. git add / git commit / git push
Changes are staged, committed, and pushed to the remote GitLab repository. Learn Git
3. GitLab detects push, triggers CI pipeline
The push event is detected by GitLab, initiating the pipeline defined in .gitlab-ci.yml. Learn CI Pipelines
4. GitLab Runner picks up the job
An available GitLab Runner claims the pending job to execute the pipeline instructions.
5. Install dependencies
The runner executes npm ci to fetch required node modules.
6. Run tests
Automated tests run using jest to ensure the new code doesn't break existing functionality.
Key Insight: Automated testing in CI prevents broken code from reaching production.
7. Build the application
The code is compiled (e.g., npm run build, tsc) to generate production-ready artifacts.
8. Docker build
A Docker image is created from a Dockerfile packaging the built app and its runtime. Learn Docker Build
9. docker tag
The new image is tagged with a semantic version or a git commit SHA.
10. docker push
The tagged image is pushed to the GitLab Container Registry. Learn Registries
Key Insight: The container registry acts as the source of truth for all deployable artifacts.
11. CI updates Helm values.yaml
A script in the CI pipeline edits the values.yaml of the Helm chart to point to the new image tag. Learn Helm
12. CI commits and pushes to GitOps repo
The modified values.yaml is committed and pushed to a separate GitOps configuration repository.
13. Argo CD detects change
Argo CD, monitoring the GitOps repo, notices a drift between the repo state and the cluster state. Learn GitOps
Key Insight: GitOps separates CI (building images) from CD (applying state to clusters).
14. Argo CD syncs
Argo CD automatically applies the new Helm chart rendering to the Kubernetes cluster.
15. Kubernetes Scheduler places Pods
The K8s control plane determines which Worker Node should run the new Pod. Learn K8s Basics
16. kubelet pulls image and starts container
The kubelet on the assigned node pulls the image from the registry and starts it via the container runtime.
17. Readiness probe passes
The container starts accepting traffic and responds 200 OK to the readiness probe. The Pod is marked Ready.
18. Service routes traffic
The Kubernetes Service adds the new Pod's IP to its endpoints, enabling internal traffic routing.
19. Ingress Controller receives request
An external user navigates to the app. The AWS Load Balancer routes it to the K8s Ingress Controller. Learn Networking
20. TLS terminated, request forwarded
The Ingress Controller handles SSL/TLS termination and passes the HTTP request to the Service.
21. Request reaches Pod
The Service routes the request to our newly deployed NestJS Pod.
22. Query PostgreSQL
NestJS queries the underlying PostgreSQL database for data.
23. Response sent to browser
The data flows back through the Service, Ingress, and Load Balancer to the user's browser.
Key Insight: Microservices abstract the complexity so the end-user just experiences a fast website.
24. Prometheus scrapes metrics
Prometheus continuously scrapes the `/metrics` endpoint of the new Pod to collect CPU, memory, and HTTP stats. Learn Prometheus
25. Grafana displays dashboard
An engineer views real-time application health on a Grafana dashboard, concluding a successful deployment. Learn Grafana
