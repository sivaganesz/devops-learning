💡 What Is It?

Terraform is an open-source Infrastructure as Code (IaC) tool by HashiCorp. It allows you to define both cloud and on-premise resources in human-readable configuration files that you can version, reuse, and share. Instead of clicking through a web console to create servers, networks, and databases, you write code that Terraform executes via cloud provider APIs.

🎯 Why Do We Need It?

Before IaC (ClickOps)

You log into the AWS Console and click through screens to create a VPC, subnets, and an EKS cluster. It takes hours. When you need a staging environment, you have to remember exactly what you clicked. Configuration drift occurs because humans make mistakes, and there is no version control or audit trail for infrastructure changes.

After IaC (Terraform)

Your entire infrastructure is defined in code. Spinning up a complete replica for staging takes a single terraform apply command. All changes go through pull requests, so team members can review them. The code acts as live documentation of your architecture.

🧠 Mental Model

🧠 Mental Model

Think of Terraform as the construction crew that builds the factory (networks, clusters, databases). GitOps/Argo CD is the factory manager who operates the assembly line inside the factory (deploying apps to the cluster).

Terraform provisions → Infrastructure (EKS, RDS) hosts → Argo CD (GitOps) deploys → Applications
ℹ️
Terraform vs GitOps

Terraform manages infrastructure (servers, VPCs, managed Kubernetes clusters). GitOps manages applications (what runs inside Kubernetes). They are complementary. Terraform builds the cluster; GitOps deploys apps to it.

⚙️ How It Works

Terraform connects to cloud providers via Providers (plugins). You declare Resources in HCL (HashiCorp Configuration Language).

When you run Terraform, it compares your desired code state against the real-world infrastructure and an internal tracking file called State (terraform.tfstate). It calculates the difference and creates an execution plan.

Core Concepts

  • Providers: Plugins that interact with cloud APIs (e.g., AWS, Azure, GCP).
  • Resources: The actual objects being created (e.g., aws_vpc).
  • Data Sources: Read-only fetches of existing data (e.g., finding the latest Ubuntu AMI).
  • Variables: Input parameters for your modules.
  • Outputs: Return values exposed after execution (e.g., a database connection string).
  • State: JSON file mapping your code resources to actual cloud IDs.

🔗 How This Applies to TaskFlow

TaskFlow Project

TaskFlow Infrastructure

We use Terraform to provision the foundational AWS environment for TaskFlow. This includes a VPC with public and private subnets, an RDS PostgreSQL database instance in the private subnet, and the EKS cluster itself. Once Terraform finishes applying, our cluster is ready for Argo CD to take over.

Example HCL: Provisioning a VPC

hcl 
provider "aws" {
  region = "us-east-1"
}

module "vpc" {
  source = "terraform-aws-modules/vpc/aws"
  version = "5.0.0"

  name = "taskflow-vpc"
  cidr = "10.0.0.0/16"

  azs             = ["us-east-1a", "us-east-1b", "us-east-1c"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24", "10.0.103.0/24"]

  enable_nat_gateway = true
}
↑ Using a public module to create a complex network architecture easily.

💻 Commands & Configuration

bash 
# Initialize working directory, download providers/modules
terraform init

# Validate syntax
terraform validate

# Create an execution plan (dry run)
terraform plan

# Apply the changes to reach desired state
terraform apply

# Destroy all resources managed by this configuration
terraform destroy

# Manage state
terraform state list
terraform state show aws_vpc.main
↑ The standard Terraform workflow commands.

⚠️ Common Mistakes

❌ Committing state files with secrets
✅ Fix: Terraform state files often contain sensitive data (like DB passwords) in plaintext. Never commit terraform.tfstate to Git. Always use a remote backend like S3 with encryption.
❌ Applying without reviewing the plan
✅ Fix: Always run terraform plan and review output before terraform apply. A typo can accidentally destroy production databases.

🔧 Troubleshooting

  • Symptom: Error acquiring the state lock Cause: Another process is running Terraform, or a previous run crashed. Fix: Ensure no one else is running apply. If it was a crash, use terraform force-unlock <lock-id> carefully.
  • Symptom: Resource already exists Cause: The resource was created manually outside Terraform. Fix: Import the existing resource into Terraform state using terraform import.

🏋️ Practice Exercise

Hands-On Exercise

Provision a Local File

  1. Create a file main.tf containing the local provider.
  2. Define a local_file resource with filename "hello.txt" and some content.
  3. Run terraform init.
  4. Run terraform plan and observe the output.
  5. Run terraform apply. Check that the file was created.
  6. Change the content in main.tf, run plan/apply again to see the update.
  7. Run terraform destroy to clean up.

🧪 Knowledge Check

A remote backend (like AWS S3) allows multiple developers to share the state file. When combined with state locking (like DynamoDB), it prevents concurrent runs that could corrupt the infrastructure state.
