💡 What Is It?

DevSecOps (Development, Security, and Operations) is the philosophy of integrating security practices into the DevOps process. Instead of bolting security on at the very end of the software development lifecycle, DevSecOps makes security a shared responsibility for everyone.

A key concept here is shifting left. Imagine the software lifecycle as a timeline moving from left (development) to right (production). Shifting left means moving security checks, vulnerability scanning, and compliance testing as early in the timeline as possible. By catching security flaws during code commit or CI rather than in production, you save time, reduce costs, and drastically lower risk.

🎯 Why Do We Need It?

Before (Traditional Security)

Security is checked only right before release. Hardcoded passwords are found in the Git repository months after being committed. Applications run as root containers. A single compromised pod gives attackers access to the entire cluster and all its secrets.

After (DevSecOps)

Developers are blocked from pushing code containing secrets. CI pipelines automatically scan Docker images for CVEs and fail if critical vulnerabilities exist. Containers run with minimal privileges. Secrets are securely managed by external tools and synced only when needed.

🧠 Mental Model

🧠 Mental Model

Think of DevSecOps like airport security. In the old days, you'd only get checked right before boarding the plane (a huge bottleneck). Today, there are checks at multiple layers: ID verification at check-in, TSA screening for bags, continuous surveillance, and finally a boarding pass check. DevSecOps implements these layered security checks throughout your software delivery pipeline.

Code Commit → CI Scanning (SAST/Images) → Infrastructure Security (RBAC/IAM) → Runtime Security

⚙️ How It Works

DevSecOps spans multiple domains:

  • Secrets Management: Never store secrets (API keys, DB passwords) in Git, CI configs, or Docker images. Kubernetes Secrets are base64-encoded, not encrypted. Tools like HashiCorp Vault or AWS Secrets Manager handle storage and rotation, while operators like External Secrets Operator sync them securely into Kubernetes.
  • IAM and Least Privilege: Every service should have only the permissions it needs. In Kubernetes on AWS, use IAM Roles for Service Accounts (IRSA) to grant specific pods access to specific AWS resources, rather than giving broad permissions to the entire worker node.
  • Container Security: Avoid running containers as root. Drop unnecessary Linux capabilities, use read-only root filesystems, and leverage distroless images to reduce the attack surface.
  • Image Scanning: Use tools like Trivy to scan container images and code dependencies for known vulnerabilities (CVEs) during the CI pipeline.
  • Network Security: Implement Kubernetes Network Policies to enforce a "default deny" rule, explicitly allowing only necessary traffic. Use TLS for all communication.

🔗 How This Applies to TaskFlow

TaskFlow Project

Securing the TaskFlow Architecture

In our TaskFlow app:

  • We store the DATABASE_URL and JWT_SECRET securely in AWS Secrets Manager, not in Git. The External Secrets Operator syncs them to Kubernetes.
  • Our backend Dockerfile uses a distroless base image and specifies USER 1001 to avoid running as root.
  • Our GitLab CI pipeline runs trivy image taskflow-api:latest to catch critical vulnerabilities before pushing to the registry.
  • We apply a Kubernetes Network Policy that only allows traffic to the database from our backend pods, blocking all other access.

💻 Commands & Configuration

Running Trivy in CI/CD:

bash 
trivy image --severity HIGH,CRITICAL taskflow-api:latest
↑ Scans the built image for HIGH and CRITICAL vulnerabilities and fails if any are found.

Secure Pod Security Context:

yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: taskflow-backend
spec:
  template:
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 1001
      containers:
      - name: backend
        image: taskflow-api:1.2.0
        securityContext:
          readOnlyRootFilesystem: true
          allowPrivilegeEscalation: false
          capabilities:
            drop:
              - ALL
↑ Enforces least privilege on the container, preventing root access and modification of the filesystem.

Kubernetes Network Policy (Default Deny):

yaml 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: taskflow
spec:
  podSelector: {} # Selects all pods in the namespace
  policyTypes:
  - Ingress
  - Egress
↑ Drops all ingress and egress traffic by default. You must create explicit allow rules for required traffic.

⚠️ Common Mistakes

❌ Mistake: Storing secrets in plain base64 in a public Git repository.
✅ Fix: Base64 is encoding, not encryption. Anyone can decode it. Use Sealed Secrets, External Secrets, or a tool like SOPS to encrypt values before committing them.
❌ Mistake: Using the `latest` image tag in production.
✅ Fix: Image tags are mutable; an attacker could replace `latest` with a malicious image. Use specific version tags or, better yet, immutable SHA256 digests (e.g., `nginx@sha256:abc123...`).

🔧 Troubleshooting

  • Symptom: Container crashes immediately with "Read-only file system". Cause: The application is trying to write logs or temporary data to the root filesystem while `readOnlyRootFilesystem: true` is set. Fix: Mount an `emptyDir` volume to the specific directories where the app needs write access (like `/tmp`).
  • Symptom: Pods cannot connect to the database after applying a default deny NetworkPolicy. Cause: The NetworkPolicy is blocking egress traffic to the database pod or external IP. Fix: Create a targeted NetworkPolicy that explicitly allows egress from the backend pods to the database port.

🏋️ Practice Exercise

Hands-On Exercise

Secure a Vulnerable Container

  1. Create a simple Dockerfile using an old, vulnerable base image (e.g., FROM node:10).
  2. Install Trivy locally and scan the image: trivy image my-vulnerable-app:latest. Observe the high number of CVEs.
  3. Update the Dockerfile to use a modern, distroless image or a current Alpine tag (e.g., FROM node:18-alpine).
  4. Add a user block to run as non-root: USER 1001.
  5. Rebuild and rescan the image with Trivy. Note the drastic reduction in vulnerabilities!

🧪 Knowledge Check

Kubernetes Secrets use base64 encoding, which provides no cryptographic security—it is easily decoded by anyone who has access to the repository. You must encrypt the secret using tools like Sealed Secrets or sync it from an external provider.

It mounts the container's root filesystem as read-only, preventing attackers who gain access to the container from modifying system binaries, installing malware, or altering application code at runtime.
