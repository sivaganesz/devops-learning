Dockerfile & Docker Compose

Master the art of building optimized container images and orchestrating multi-container environments using Docker Compose.

💡 What Is It?

A Dockerfile is a text document that contains all the commands a user could call on the command line to assemble an image. It's infrastructure as code for your application's environment.

Docker Compose is a tool for defining and running multi-container Docker applications. With Compose, you use a YAML file to configure your application's services (e.g., frontend, backend, database), networks, and volumes, allowing you to create and start the entire stack with a single command.

🎯 Why Do We Need It?

Before Compose

To run an app requiring a DB and backend, you had to manually create a network, run the database container, figure out its IP, run the backend container passing the DB IP as an environment variable. Highly manual and error-prone.

After Compose

You define all relationships in one docker-compose.yml file. Running docker compose up automatically creates the network, starts the database, and starts the backend, linking them together seamlessly via DNS resolution.

🧠 Mental Model

🧠 Mental Model: The Architect and the Contractor

A Dockerfile is the blueprint for a single building (an image). Docker Compose is the city planner's map that shows how multiple buildings (services) connect via roads (networks) and where they share resources (volumes).

App Code → Dockerfile (Single Image) → Compose (Full Stack)

⚙️ How It Works: Volumes & Networks

Docker Volumes: Persistent Data

By default, data inside a container is lost when the container is removed. Volumes solve this:

  • Named Volumes: Managed by Docker, stored in Docker's internal directory on the host. Best for databases (e.g., PostgreSQL data).
  • Bind Mounts: Maps a specific host directory to a container directory. Perfect for local development to sync code changes instantly.

Docker Networks: Container Communication

Containers need to talk to each other. Docker uses software-defined networking:

  • Bridge Network: The default. Custom bridge networks provide automatic DNS resolution between containers using their container names.
  • Host Network: Removes network isolation; the container uses the host's network.

📚 Core Dockerfile Instructions

Instruction Purpose Example
FROM Base image to start from. FROM node:20-alpine
WORKDIR Sets the working directory inside container. WORKDIR /app
COPY Copies files from host into container. COPY package.json ./
RUN Executes shell commands during build. RUN npm ci
CMD Default command when container starts. CMD ["npm", "start"]

🔗 How This Applies to TaskFlow

TaskFlow Project

Optimizing our Images

For the TaskFlow backend (NestJS), if we don't use multi-stage builds, our image includes the TypeScript compiler, devDependencies, and raw source code, making it over 1GB. By using multi-stage builds, we compile in stage 1, then only copy the compiled JS and production dependencies to stage 2, reducing the image size to under 200MB and vastly improving security.

💻 Commands & Configuration

TaskFlow Backend Dockerfile (Multi-stage)

docker 
# Stage 1: Build
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: Production
FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
# Copy package files and install only prod deps
COPY package*.json ./
RUN npm ci --only=production
# Copy compiled output from builder stage
COPY --from=builder /app/dist ./dist
USER node
CMD ["node", "dist/main.js"]
↑ Multi-stage build for NestJS ensuring minimal attack surface and size.

TaskFlow Docker Compose

yaml 
version: '3.8'

services:
  db:
    image: postgres:15-alpine
    environment:
      POSTGRES_USER: taskflow
      POSTGRES_PASSWORD: secretpassword
      POSTGRES_DB: taskflow_db
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - taskflow_net

  api:
    build: 
      context: ./backend
    ports:
      - "3000:3000"
    environment:
      - DB_HOST=db
      - DB_USER=taskflow
      - DB_PASS=secretpassword
    depends_on:
      - db
    networks:
      - taskflow_net

volumes:
  pgdata:

networks:
  taskflow_net:
↑ Entire application stack managed in one file. Notice how `DB_HOST=db` resolves automatically.

⚠️ Common Mistakes

❌ Inefficient Layer Caching

Writing COPY . . before RUN npm install.

✅ Fix: Always copy package.json and run npm install BEFORE copying the rest of the source code. This ensures Docker uses the cached node_modules layer unless package.json changes.

🔧 Troubleshooting

  • Symptom: Database container loses data on restart. Cause: You didn't map a volume for the database data directory. Fix: Add a volume mapping like -v pgdata:/var/lib/postgresql/data.
  • Symptom: Container A cannot reach Container B. Cause: They are on different networks, or relying on IP instead of Compose service name DNS. Fix: Ensure both are on the same custom bridge network and use the service name as the hostname.

🏋️ Practice Exercise

Hands-On Exercise

Caching Check

  1. Create a Dockerfile with COPY . . followed by RUN npm install. Build it.
  2. Change a single line in a source file, and build again. Notice npm install runs entirely from scratch.
  3. Modify the Dockerfile to copy package.json, run install, then copy source. Build twice with source changes. Notice the massive speedup!

🧪 Knowledge Check

depends_on only ensures the database container starts before the API container. It does NOT wait for the database process inside (e.g., PostgreSQL) to finish its internal startup sequence and be ready to accept connections. You need healthchecks for robust startup ordering.
