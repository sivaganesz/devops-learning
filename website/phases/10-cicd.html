CI/CD with GitLab

Automate your build, test, and deployment workflows. Learn how to write robust GitLab CI pipelines to ensure quality and speed in software delivery.

💡 What Is It?

Continuous Integration (CI) is the practice of automating the integration of code changes from multiple contributors into a single software project. Automated tests are run against every commit to catch bugs early.

Continuous Delivery (CD) automates the release process so that the software can be deployed to production at any time by simply clicking a button.

Continuous Deployment (CD) goes one step further: every change that passes all stages of your production pipeline is released to your customers automatically, with no human intervention.

🎯 Why Do We Need It?

Before CI/CD

Code integrations were manual and infrequent, leading to "merge hell." Developers forgot to run tests locally, deploying broken code. Deployments required SSHing into servers, running fragile scripts, and crossing fingers.

After CI/CD

Every commit is automatically tested in an isolated environment. The pipeline builds immutable Docker images. Deployments are automated, auditable, and repeatable. Fear of deployment disappears.

🧠 Mental Model

🧠 Mental Model: The Assembly Line

Think of CI/CD as an automated factory assembly line. The code is the raw material. It goes through various stations (stages): quality check (tests), packaging (docker build), safety inspection (security scan), and finally, shipping (deploy).

Git Push → GitLab CI (Tests & Build) → Container Registry

⚙️ How It Works: GitLab CI Architecture

GitLab CI uses a distributed architecture:

  • GitLab Server: Stores the code, parses the .gitlab-ci.yml file, and acts as the orchestrator dispatching jobs.
  • GitLab Runner: A lightweight agent installed on separate servers (or containers) that executes the jobs.
    • Docker Executor: The most common runner type. For every job, the runner starts a fresh Docker container, runs the job script inside it, and throws the container away. This ensures a clean, reproducible environment every time.

📚 Core Concepts

Term Definition
Pipeline The top-level component representing a full workflow. Triggered by a push or MR.
Stage A logical grouping of jobs. Stages run sequentially (e.g., test then build).
Job A single task that runs commands. Jobs in the same stage run in parallel.
Artifacts Files generated by a job (like compiled binaries) that can be passed to later stages or downloaded.
Cache Files (like node_modules) saved between pipeline runs to speed up execution.

🔗 How This Applies to TaskFlow

TaskFlow Project

Automating Our Monorepo

For TaskFlow, we want to run backend unit tests (NestJS) and frontend tests (React) concurrently. If they pass, we build the Docker images and push them to the GitLab Container Registry tagged with the Git commit hash. Finally, we trigger a deployment to staging.

💻 Configuration (.gitlab-ci.yml)

yaml 
stages:
  - test
  - build
  - security
  - deploy

variables:
  # Predefined variables are used for registry auth
  IMAGE_TAG: $CI_REGISTRY_IMAGE/api:$CI_COMMIT_SHA

# --- TEST STAGE ---
test-backend:
  stage: test
  image: node:20-alpine
  cache:
    key: "backend-node-modules"
    paths:
      - backend/node_modules/
  script:
    - cd backend
    - npm ci
    - npm run test

# --- BUILD STAGE ---
build-api:
  stage: build
  image: docker:24.0.5
  services:
    - docker:24.0.5-dind
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
  script:
    - cd backend
    - docker build -t $IMAGE_TAG .
    - docker push $IMAGE_TAG

# --- SECURITY STAGE ---
scan-image:
  stage: security
  image: aquasec/trivy:latest
  script:
    - trivy image --severity HIGH,CRITICAL $IMAGE_TAG
  allow_failure: true # Don't block pipeline on vulns (for now)

# --- DEPLOY STAGE ---
deploy-staging:
  stage: deploy
  image: bitnami/kubectl:latest
  environment:
    name: staging
  script:
    - echo "Updating GitOps repo with new tag $IMAGE_TAG"
    # Logic to update manifest in gitops repo
  only:
    - main
↑ Complete pipeline for the TaskFlow backend. Demonstrates stages, cache, Docker-in-Docker (dind) builds, and environments.

⚠️ Common Mistakes

❌ Hardcoding Secrets in Scripts

Writing `docker login -u user -p mySecretPassword` directly in the `.gitlab-ci.yml`.

✅ Fix: Use GitLab CI/CD Variables (Settings > CI/CD > Variables). Mark secrets as Masked so they are scrubbed from job logs, and Protected so they are only exposed to protected branches (like main).

🔧 Troubleshooting

  • Symptom: Pipeline fails at `docker login` with authentication error. Cause: Runner doesn't have access to registry credentials. Fix: Ensure you use the predefined $CI_REGISTRY_USER and $CI_REGISTRY_PASSWORD.
  • Symptom: Job fails with "command not found". Cause: The command doesn't exist inside the Docker image defined in the image: tag for that job. Fix: Pick an image that has the tools you need, or add a before_script to apk add/apt-get install the tool.

🧪 Knowledge Check

Cache is used for ephemeral dependencies (like `node_modules`) to speed up subsequent pipeline runs. It is not guaranteed to exist. Artifacts are the intentional output of a job (like a compiled binary or test report) that are guaranteed to be passed to subsequent stages and can be downloaded from the UI.
