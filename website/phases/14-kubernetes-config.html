Kubernetes Config & Operations

Injecting configuration securely, managing persistent state, setting resource limits, and auto-scaling workloads in production.

⚠️ Prerequisites
  • Phase 12: Kubernetes Core
  • Phase 13: Kubernetes Networking
✅ What You Will Learn
  • Managing environment variables with ConfigMaps and Secrets.
  • Using Persistent Volumes (PV) and Claims (PVC) for databases.
  • Ensuring application health with Liveness and Readiness probes.
  • Managing application lifecycles, HPA, and Resource requests/limits.

💡 What Is It?

Deploying stateless containers is easy, but real applications need injected configuration, sensitive secrets, stateful database storage, and operational guarantees. K8s Config and Operations encompass the resources (ConfigMaps, PVs, HPAs) that make your applications robust, state-aware, and highly available.

🎯 Why Do We Need It?

Before

You bake configuration files into your Docker images, meaning you have to rebuild images for every environment (dev/prod). Database containers lose all data if they restart. Heavy traffic crashes your single container.

After

You inject settings dynamically via ConfigMaps. Databases write to Persistent Volumes that survive pod deletion. Horizontal Pod Autoscalers dynamically add replicas when CPU usage spikes.

🧠 Mental Model

🧠 Mental Model

Think of the Container as an empty video game console. ConfigMaps/Secrets are the game cartridges you plug in. Persistent Volumes are the memory cards saving your progress. Probes are the heartbeat monitor checking if the console froze.

ConfigMap → Pod Spec → PVC → PV / EBS Volume

⚙️ How It Works

ConfigMaps & Secrets: You create these objects in the API server. Pods reference them in their YAML, and Kubelet dynamically mounts them into the container as either environment variables or files on the filesystem.

Storage: A Pod requests storage via a PersistentVolumeClaim (PVC). Kubernetes matches it with an available PersistentVolume (PV) or uses a StorageClass to dynamically provision cloud storage (like AWS EBS).

Probes & Limits: Requests guarantee baseline CPU/RAM; Limits enforce a hard ceiling to prevent resource hogging. Liveness probes reboot deadlocked apps, while Readiness probes stop traffic to booting apps.

📚 Core Concepts

🗂️
ConfigMap & Secret
Decouples configuration from images. Secrets are base64 encoded. Neither are encrypted at rest by default without add-ons.
💾
PV & PVC
PV is the actual storage piece; PVC is a ticket requesting storage size/access mode for a Pod.
🩺
Probes
Liveness (kill and restart), Readiness (add/remove from Service endpoints), Startup (delay other checks).

🔗 How This Applies to TaskFlow

TaskFlow Project

Our Running Example

In TaskFlow, the NestJS backend uses a ConfigMap for `LOG_LEVEL` and a Secret for `DATABASE_URL` and `JWT_SECRET`. The PostgreSQL StatefulSet uses a PVC to request a 10Gi AWS EBS volume to store the database files persistently. We configure an HPA to auto-scale the backend Deployment from 2 to 10 replicas if CPU exceeds 70%.

💻 Commands & Configuration

yaml 
# taskflow-deployment-probes.yaml snippet
spec:
  containers:
  - name: backend
    image: my-backend:v1
    resources:
      requests:
        memory: "256Mi"
        cpu: "250m"
      limits:
        memory: "512Mi"
        cpu: "500m"
    envFrom:
    - configMapRef:
        name: backend-config
    livenessProbe:
      httpGet:
        path: /health
        port: 3000
      initialDelaySeconds: 15
    readinessProbe:
      httpGet:
        path: /health
        port: 3000
      periodSeconds: 5
↑ Configuring requests/limits, envFrom for ConfigMaps, and HTTP probes.

⚠️ Common Mistakes

❌ Committing raw Secrets to Git
✅ Fix: Use tools like Sealed Secrets or External Secrets Operator (integrating with AWS Secrets Manager/Vault) to inject secrets safely.
❌ Forgetting Resource Requests/Limits
✅ Fix: A pod without limits can consume all node CPU/RAM, crashing other workloads. Always set requests and limits.

🔧 Troubleshooting

  • Symptom: Pod is OOMKilled Cause: The container exceeded its memory `limit`. Fix: Profile the application for memory leaks or increase the memory limit in the Deployment YAML.
  • Symptom: PVC stuck in Pending state Cause: K8s cannot provision the volume, often due to a missing/default StorageClass. Fix: Ensure the cloud-controller-manager is working and the StorageClass exists (`kubectl get sc`).

Hands-On Exercise

Create a ConfigMap

  1. Run `kubectl create configmap app-settings --from-literal=theme=dark`.
  2. Create a Pod YAML that injects `theme` as an env var.
  3. Apply the Pod, then run `kubectl exec -- env | grep theme` to verify.

🧪 Knowledge Check

Liveness probe determines if the container needs to be forcefully restarted. Readiness probe determines if the container is currently able to accept traffic (if it fails, the Pod is removed from Service routing, but not killed).
