OS & Computer Concepts

💡 What Is It?

The Operating System (OS) is the master control program that manages a computer's hardware and provides common services for computer programs. When you execute code, you are not talking directly to the CPU or RAM; you are making requests to the OS Kernel.

For DevOps, understanding OS concepts is vital because tools like Docker are not magic—they are simply clever wrappers around OS primitives (like namespaces and cgroups) to isolate processes.

🎯 Why Do We Need It?

Before

Treating servers as "black boxes" where you just run code. When an application crashes with "port already in use" or "out of memory", you are left guessing and blindly rebooting servers.

After

You understand exactly how processes request resources, how they bind to ports, and where their logs go (stdout). Troubleshooting becomes a scientific process of inspecting process state and file descriptors.

🧠 Mental Model

🧠 Mental Model

Think of the OS Kernel as a strict restaurant manager. Programs (customers) cannot just walk into the kitchen (Hardware/CPU/RAM) and start cooking. They must ask the manager (Kernel via system calls) for a table (memory) and food (I/O). The manager decides who gets time in the kitchen (CPU scheduling).

Source Code (Disk) → Process (Memory/PID) → Kernel (Syscalls) → Hardware (CPU)

⚙️ How It Works

Program vs. Process: A program is a static file on disk (like `dist/main.js`). A process is that code actively running in memory. The OS assigns it a unique Process ID (PID).

Memory Layout: A process gets memory divided into sections:

  • Stack: Stores local variables and function calls. A "stack overflow" happens when functions call each other too many times (infinite recursion), running out of stack space.
  • Heap: Dynamic memory allocated at runtime (objects, arrays). If a process forgets to free heap memory, you get a "memory leak."
  • Code/Text: The actual compiled instructions.

CPU Scheduling: A single CPU core can only do one thing at a time. The kernel uses time-slicing and context switching—giving each process a tiny fraction of a second on the CPU—to make it look like hundreds of processes are running simultaneously.

Ports and Sockets: A machine has one IP address but can run many services. Ports (0-65535) act as apartment numbers. The OS binds a process to a port via a network socket. 80=HTTP, 443=HTTPS, 3000=NestJS, 5432=PostgreSQL.

File Descriptors (FDs): Everything in Linux is a file, including network connections and screen output. Every process gets 3 default FDs: 0 = Standard Input (stdin), 1 = Standard Output (stdout), and 2 = Standard Error (stderr). This is why Docker collects container logs simply by reading stdout/stderr!

🔗 How This Applies to TaskFlow

TaskFlow Project

Our Running Example

When we run our TaskFlow backend using node dist/main.js:

  1. The OS reads the `node` binary from disk and creates a Process.
  2. It allocates Memory (Stack/Heap) for the NestJS app to run.
  3. NestJS makes a system call to bind a Socket to Port 3000.
  4. When console.log('App running') is called, it writes to File Descriptor 1 (stdout).

💻 Commands & Configuration

bash 
# See running processes
ps aux

# See live process CPU/Memory usage
top

# Find which process is listening on port 3000
lsof -i :3000

# Kill a stuck process by its PID (e.g., 1234)
kill -9 1234
↑ These commands allow you to peer into the OS and manage processes manually.

⚠️ Common Mistakes

❌ Writing logs to a file inside a container
✅ Fix: Always log to stdout and stderr in modern DevOps (12-factor apps). The infrastructure (Docker/Kubernetes) handles capturing those file descriptors.

🔧 Troubleshooting

  • Symptom: Error: EADDRINUSE :::3000 Cause: Another process (usually an old instance of your app) is already bound to port 3000. Fix: lsof -i :3000 to find the PID, then kill <PID>.

🏋️ Practice Exercise

Hands-On Exercise

Inspect Your OS State

  1. Open a terminal (Linux/macOS/Git Bash).
  2. Run top and identify which process is using the most CPU. Press q to exit.
  3. Start a temporary web server: python3 -m http.server 8080 (or run any app).
  4. Open a new terminal tab and run lsof -i :8080. Find the PID.
  5. Kill it using kill <PID>. Observe the first terminal stop running the server.

🧪 Knowledge Check

Because standard output (stdout, FD 1) is a universal stream managed by the OS. Docker simply connects to this stream and routes the logs wherever needed, without needing to know where your specific application stores files on disk.
