Networking Fundamentals

Understand IP addresses, DNS, TCP/IP, and HTTP — the foundation for all DevOps, Docker, and Kubernetes communication.

⚠️ Prerequisites
  • Phase 03: Linux Basics (knowing how to run commands in the terminal)
✅ What You Will Learn
  • How computers talk across networks using IP addresses and Ports.
  • How DNS resolves names to IP addresses.
  • The OSI Model and core protocols (TCP, UDP, HTTP).
  • Essential Linux networking commands for troubleshooting.

💡 What Is It?

Networking is the invisible plumbing that connects every piece of software you run. In DevOps, networking is everywhere: Docker uses virtual bridge networks, Kubernetes uses complex overlay networks and Service IPs, AWS uses Virtual Private Clouds (VPCs), and Load Balancers route HTTP traffic from the public internet into your private servers.

Without a solid grasp of IP addressing, subnets, ports, and DNS, you simply cannot debug a failing deployment. When an application can't connect to a database, 90% of the time it's a networking issue, not a code issue.

🎯 Why Do We Need It?

Before

You run an app locally on localhost:3000. It works on your machine because there are no firewalls, no subnets, and no routing tables between the frontend and the backend. Everything is implicitly trusted.

After

In production, your app runs in a private cloud subnet, behind a load balancer, with strict firewall rules. Understanding networking allows you to securely expose the app to the internet while keeping databases hidden, and to troubleshoot when parts of the system can't talk to each other.

🧠 Mental Model

🧠 Mental Model

Think of networking like the postal system. The IP address is the street address of an apartment building (the server). The Port is the apartment number (the specific app running on that server). DNS is the contact book on your phone, translating a name like "Alice" into her actual address.

Browser → DNS Resolution → Load Balancer IP → Port 443 (TLS) → HTTP Server (NestJS:3000)

⚙️ How It Works

The OSI Model (Simplified)

Networking happens in layers. A simplified 4-layer model is all you need for DevOps:

  • Application Layer: HTTP/HTTPS. The actual data being sent (JSON, HTML).
  • Transport Layer: TCP/UDP. Ensures the data gets there reliably and in order (TCP) or quickly without guarantees (UDP). Defines the Port number.
  • Internet Layer: IP (Internet Protocol). Handles IP addresses and routing packets across different networks.
  • Network Access Layer: Ethernet/MAC addresses. The physical cables and local switches.

IP Addresses & CIDR

An IPv4 address (e.g., 192.168.1.5) is 32 bits long, divided into 4 octets. Because public IPs ran out, we use Private IP ranges (10.x.x.x, 172.16-31.x.x, 192.168.x.x) for internal networks.

CIDR Notation defines subnets (network sizes). /32 is a single IP. /24 means 256 IPs (common for home networks, e.g., 192.168.1.0/24). /16 means 65,536 IPs (common for AWS VPCs, e.g., 10.0.0.0/16).

TCP vs UDP & Ports

TCP uses a 3-way handshake (SYN, SYN-ACK, ACK) to establish a reliable connection. Used for HTTP, SSH, Databases. UDP just fires packets blindly. Used for DNS, video streaming.

Ports identify the application. 0-1023 are privileged well-known ports (80 HTTP, 443 HTTPS, 22 SSH). Above that are ephemeral ports and application ports (5432 Postgres, 3000 Node, 5173 Vite).

🔗 How This Applies to TaskFlow

TaskFlow Project

Our Running Example

When you deploy TaskFlow:

  • Your backend (NestJS) listens on port 3000. Your database (PostgreSQL) listens on port 5432.
  • You will configure a private Docker network so the backend can talk to the database using the internal DNS name db, but the database is not exposed to the public internet.
  • A reverse proxy (like Nginx) listens on port 80/443 on the public IP, handles the TLS decryption, and forwards the HTTP traffic to the internal NestJS container on port 3000.

💻 Commands & Configuration

bash 
# Check what ports are actively listening on your machine
ss -tulpn
↑ Shows TCP/UDP sockets, listening state, processes, and port numbers. Essential for finding what is blocking port 3000!
bash 
# Perform a DNS lookup to see the IP of a domain
dig google.com +short
↑ Queries DNS servers to return the A record (IPv4 address) of the domain.
bash 
# Test if a specific port is open and reachable on a remote host
nc -zv 192.168.1.50 5432
↑ Netcat tries to open a TCP connection to the IP on port 5432. Great for testing if a firewall is blocking your DB.

⚠️ Common Mistakes

❌ Mistake: Binding to localhost (127.0.0.1) inside a container
✅ Fix: When running inside Docker or a VM, your app must bind to 0.0.0.0 (all interfaces) to receive traffic from outside the container. If NestJS binds to 127.0.0.1, the port mapping will fail.

🔧 Troubleshooting

  • Symptom: "Connection Refused" Cause: The server IP is reachable, but absolutely nothing is listening on that port. Either the app crashed, or you typed the wrong port. Fix: SSH into server and run ss -tulpn to check listening ports.
  • Symptom: "Connection Timeout" Cause: Packets are being dropped into a black hole. Almost always a Firewall (AWS Security Group) or routing issue. Fix: Check firewall rules allowing ingress on that specific port.

🏋️ Practice Exercise

Hands-On Exercise

Investigate Your Local Network

  1. Run ip addr show (Linux) or ipconfig (Windows) to find your computer's private IP address.
  2. Run dig github.com to see how DNS resolves GitHub's IP address. Note the "Query time".
  3. Run curl -v https://google.com. Read the verbose output to see the DNS resolution, TCP handshake, TLS handshake, and HTTP headers in real time.

🧪 Knowledge Check

Security and IPv4 scarcity. Servers with private IPs cannot be reached directly from the internet, protecting them from hackers. They also don't consume limited public IPv4 addresses.

Connection Refused means the host was reached but rejected the connection (usually no app listening). Timeout means the packet never got a response, usually blocked by a firewall.
