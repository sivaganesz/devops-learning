💡 What Is It?

Advanced DevOps moves beyond simply getting an application to run, focusing entirely on resilience, scalability, and operational excellence at scale. It incorporates site reliability engineering (SRE) practices to ensure systems remain fast and highly available during unpredictable traffic spikes and complex updates.

🎯 Why Do We Need It?

Before

Traffic spikes cause application crashes. Deployments involve manual scripts, causing 10 minutes of downtime for users. Database outages lead to massive data loss. Teams operate on gut feelings rather than metrics.

After

The cluster automatically adds nodes and pods when traffic surges. Deployments route 5% of traffic to the new version automatically verifying health. The database has a hot standby. SLIs and error budgets dictate release velocity.

⚙️ How It Works

Autoscaling has three primary dimensions in Kubernetes:

  • HPA (Horizontal Pod Autoscaler): Adds or removes Pod replicas based on CPU, memory, or custom metrics (e.g., requests per second).
  • VPA (Vertical Pod Autoscaler): Adjusts the CPU/memory requests and limits of existing Pods based on historical usage.
  • Cluster Autoscaler & Karpenter: Add or remove actual compute nodes (EC2 instances) when Pods cannot be scheduled due to lack of resources.

Deployment Strategies:

  • Rolling Update (default): Gradually replace old pods with new pods. Zero downtime, but both versions coexist temporarily.
  • Blue/Green: Stand up a completely new environment (green), test it, and instantly flip the load balancer traffic to it. Easy rollback.
  • Canary: Slowly route a small percentage (e.g., 5%) of traffic to the new version. Monitor metrics, then gradually increase to 100%. Argo Rollouts is popular for this.

SRE Fundamentals:

  • SLI (Service Level Indicator): A metric you measure (e.g., HTTP 5xx error rate).
  • SLO (Service Level Objective): Your target (e.g., 99.9% of requests must succeed over 30 days).
  • Error Budget: The allowed failure rate (e.g., 0.1%). If you burn through it, you stop releasing features and focus purely on reliability.

📚 Core Concepts

📈
KEDA
Kubernetes Event-Driven Autoscaling. Allows scaling pods based on external metrics like AWS SQS queue length or database connections. Can scale to zero.
🔄
Pod Disruption Budget (PDB)
Ensures a minimum number of replicas are always available during voluntary disruptions like node upgrades or evictions.
🚧
Toil
Manual, repetitive, automatable work. SREs aim to eliminate toil so they can focus on engineering improvements.

🔗 How This Applies to TaskFlow

TaskFlow Project

Advanced Operations for TaskFlow

For the TaskFlow production environment:

  • We configure an HPA on the taskflow-api deployment to scale up to 10 replicas if CPU usage exceeds 70%.
  • We define a PDB (Pod Disruption Budget) specifying minAvailable: 2 so cluster upgrades never take the API fully offline.
  • We implement a preStop hook in our API containers that sleeps for 5 seconds to allow the ALB to cleanly drain connections before the container terminates, achieving true zero-downtime deployments.
  • We set an SLO that 99.9% of API requests must return in under 500ms.

💻 Commands & Configuration

Horizontal Pod Autoscaler (HPA) YAML:

yaml 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: taskflow-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: taskflow-api
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
↑ Scales the taskflow-api deployment between 2 and 10 pods to keep average CPU utilization around 70%. (Requires metrics-server)

Zero-Downtime Deployment Tweaks:

yaml 
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 0
  template:
    spec:
      containers:
      - name: api
        lifecycle:
          preStop:
            exec:
              command: ["/bin/sh", "-c", "sleep 5"]
↑ Ensures no pods go unavailable during a rolling update, and introduces a sleep on shutdown to let the load balancer catch up.

⚠️ Common Mistakes

❌ Mistake: Using HPA without setting resource requests on the Pods.
✅ Fix: The HPA calculates CPU utilization as a percentage of the Pod's requested CPU. If requests aren't set, HPA cannot calculate the metric and will fail to scale. Always set `resources.requests.cpu`.
❌ Mistake: Breaking database schema changes during a rolling update.
✅ Fix: In a rolling update, V1 and V2 of the code run simultaneously. DB migrations must be backward-compatible (e.g., add a column but don't delete the old one yet) so both code versions work.

🔧 Troubleshooting

  • Symptom: HPA shows `<unknown>/70%` for metrics and doesn't scale. Cause: The Metrics Server is not installed in the cluster, or the Pod lacks resource requests. Fix: Install Metrics Server and ensure `resources.requests` is defined in the Deployment.
  • Symptom: Cluster Autoscaler is not spinning up new nodes when pods are Pending. Cause: The node group's maximum size limit has been reached, or IAM permissions are missing. Fix: Check the Auto Scaling Group max capacity limits in AWS and verify the cluster autoscaler pod logs.

🏋️ Practice Exercise

Hands-On Exercise

Configure and Trigger an HPA

  1. Deploy a sample Nginx deployment with `requests.cpu: 100m`.
  2. Apply an HPA targeting 50% CPU utilization.
  3. Use a load generator tool like hey or run a busybox pod with a `while true` loop hitting the Nginx service to spike CPU usage.
  4. Run kubectl get hpa -w and watch the replica count scale up as the metric exceeds the target.
  5. Stop the load and observe the HPA scale the replicas back down (after a cooldown period).

🧪 Knowledge Check

Blue/Green routes 100% of traffic instantly from the old version to the fully deployed new version. Canary routes a small percentage of traffic (e.g., 5%) to the new version initially, tests for regressions, and gradually increases traffic, minimizing the blast radius.

When Kubernetes terminates a pod, it sends a SIGTERM to the container while simultaneously updating the service endpoints. A preStop sleep ensures the application stays alive long enough to finish processing active requests and allows the load balancer time to remove the pod from rotation.
