GitOps & Argo CD

Adopt the GitOps operational model to manage your Kubernetes applications declaratively via Git, using Argo CD.

⚠️ Prerequisites
  • Phase 15: Helm (Packaging Kubernetes apps)
  • Phase 10: CI/CD Pipelines
✅ What You Will Learn
  • The 4 core principles of GitOps
  • The pull vs push model for cluster deployments
  • How Argo CD detects and corrects configuration drift
  • How to implement the Two-Repo pattern for app delivery

💡 What Is It?

GitOps is an operational model where Git is the single source of truth for the desired state of your infrastructure and applications. All changes to the cluster happen via Git commits. You never run kubectl apply or helm upgrade manually. Instead, software agents running in the cluster continuously pull the desired state from Git and apply it.

The four GitOps principles are: Declarative, Versioned and immutable, Pulled automatically, and Continuously reconciled.

🎯 Why Do We Need It?

Before GitOps (Push Deployments)

Your CI pipeline builds an image and runs helm upgrade directly against the production cluster. This means CI needs highly privileged cluster credentials. Furthermore, if someone manually edits a Deployment in the cluster, configuration drift accumulates because Git and the cluster no longer match. There is no easy audit trail of who changed what in the cluster.

After GitOps (Pull Deployments)

Your CI pipeline only updates a Helm value in a Git repository. Argo CD (running inside the cluster) detects the Git commit, pulls the new configuration, and applies it. CI has no cluster access. If someone manually changes a resource, Argo CD detects the drift and immediately rolls it back to match Git.

🧠 Mental Model

🧠 Mental Model

Think of a thermostat. You set the desired temperature (Git). The room has an actual temperature (Kubernetes cluster state). The thermostat (Argo CD) constantly monitors both and activates the heater or AC (syncs) until the actual state matches the desired state.

Git Repo (Desired State) ← observed by → Argo CD (Reconciler) ← manipulates → Kubernetes (Actual State)

⚙️ How It Works

Argo CD is a Kubernetes controller. You install it into your cluster, and it watches specific Git repositories that you configure via Application CRDs (Custom Resource Definitions).

When Argo CD sees that the live state in the cluster differs from the desired state in Git, it marks the application as OutOfSync. Depending on your configuration, it will either wait for you to manually trigger a sync, or it will automatically apply the changes.

Two-Repo Pattern

Best practice dictates separating your application source code from your deployment manifests:

  • App Repo: Contains source code, Dockerfile, and CI pipeline (runs tests, builds image, pushes to registry, then updates the GitOps repo).
  • GitOps Repo: Contains only Kubernetes manifests or Helm charts/values. This is what Argo CD watches.

🔗 How This Applies to TaskFlow

TaskFlow Project

TaskFlow GitOps Deployment

We create a new repository: gitlab.com/yourname/taskflow-gitops. Inside, we store our Helm values.yaml for staging and production. The TaskFlow App CI pipeline builds the Docker image and then runs a script to update the image tag in the GitOps repo and commit it. Argo CD, running in our AWS EKS cluster, detects the commit and syncs the new image to the taskflow namespace.

💻 Commands & Configuration

An Argo CD Application definition (declarative setup):

yaml 
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: taskflow-production
  namespace: argocd
spec:
  project: default
  source:
    repoURL: 'https://gitlab.com/yourname/taskflow-gitops.git'
    targetRevision: HEAD
    path: production
    helm:
      valueFiles:
        - values.yaml
  destination:
    server: 'https://kubernetes.default.svc'
    namespace: taskflow-prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
↑ Tells Argo CD to watch the GitOps repo and sync it to taskflow-prod, enabling self-healing.

⚠️ Common Mistakes

❌ Fighting Self-Heal
✅ Fix: If you have CI pushing directly to the cluster AND Argo CD syncing from Git with self-heal enabled, they will fight constantly. CI should only update Git; let Argo CD update the cluster.

🔧 Troubleshooting

  • Symptom: App stuck in 'Syncing' or 'OutOfSync' Cause: Kubernetes API rejected the resource (e.g., invalid YAML, missing CRDs). Fix: Check the Argo CD UI logs or use argocd app get app-name to find the specific resource error.
  • Symptom: Argo CD cannot access Git repository Cause: Missing or incorrect authentication. Fix: Ensure you've added the correct SSH private key or access token to Argo CD's repository credentials.

🏋️ Practice Exercise

Hands-On Exercise

Install and Use Argo CD

  1. Install Argo CD: kubectl create namespace argocd then apply the manifest from Argo's official docs.
  2. Port-forward the UI: kubectl port-forward svc/argocd-server -n argocd 8080:443.
  3. Create an App from a public repo (like argoproj/argocd-example-apps).
  4. Observe the sync process.
  5. Manually edit a deployment in the cluster (e.g., change replica count) and watch Argo CD's self-heal revert your change.

🧪 Knowledge Check

You use git revert on the commit that introduced the bad change in your GitOps repository. Once the revert is pushed to Git, Argo CD detects it and automatically syncs the cluster back to the previous state.
