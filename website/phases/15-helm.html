💡 What Is It?

Helm is the package manager for Kubernetes. Just as apt is for Debian or npm is for Node.js, Helm helps you manage Kubernetes applications. Instead of managing dozens of hard-coded YAML files, Helm allows you to define, install, and upgrade even the most complex Kubernetes applications as a single bundled package called a Chart.

🎯 Why Do We Need It?

Before Helm

You have dozens of YAML files for Deployments, Services, and Ingresses. To deploy to staging and production, you copy-paste the files and manually change the image tags, resource limits, and replica counts. There is no version history of deployments and rolling back means tracking down the old YAML files and applying them.

After Helm

You have one generic set of templates (a Chart). You supply different values.yaml files for staging and production. Deploying, upgrading, or rolling back an entire application is done with a single command. Helm tracks deployment history directly in the cluster.

🧠 Mental Model

🧠 Mental Model

Think of a Helm Chart like a cooking recipe template. The template gives you the instructions, but the Values are the specific ingredients you choose. When you bake it (install it), you get a finished cake (a Release).

Chart (Template) + Values (Config) = Release (Running App)

⚙️ How It Works

Helm combines a directory of templates (which look like normal Kubernetes YAML but with Go template syntax inside) with configuration values. When you run helm install, Helm renders the templates by injecting the values, producing standard Kubernetes manifests, and then applies them to the cluster.

It also keeps track of each installation as a Release in the cluster (stored as Secrets), so it knows exactly what was deployed, allowing you to upgrade or rollback effortlessly.

Chart Structure

A standard Helm chart looks like this:

bash 
taskflow-chart/
├── Chart.yaml        # chart metadata (name, version, appVersion)
├── values.yaml       # default configuration values
├── templates/        # Kubernetes manifests with template syntax
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── ingress.yaml
│   ├── configmap.yaml
│   ├── secret.yaml
│   ├── hpa.yaml
│   └── _helpers.tpl  # reusable template snippets
└── charts/          # chart dependencies (e.g., a database chart)
↑ The standard directory layout for a Helm chart.

Go Template Syntax

Helm uses Go templates to inject values into YAML:

  • {{ .Values.image.tag }}: Injects a value from values.yaml.
  • {{ .Release.Name }}: The name you gave the release when installing.
  • {{ include "taskflow.labels" . }}: Includes a reusable snippet from _helpers.tpl.
  • {{ if .Values.ingress.enabled }}: Conditionally renders blocks of YAML.
  • {{ range .Values.env }}: Iterates over lists to create multiple YAML elements.

🔗 How This Applies to TaskFlow

TaskFlow Project

Packaging TaskFlow

We will package the TaskFlow Backend and Frontend into a single taskflow-chart. Instead of hardcoding environment variables or replica counts, we expose them in values.yaml. In GitLab CI, our deploy job will run helm upgrade --install passing in the new $CI_COMMIT_SHA as the image tag, ensuring seamless updates.

Example TaskFlow Deployment Template

yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "taskflow.fullname" . }}
  labels:
    {{- include "taskflow.labels" . | nindent 4 }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      {{- include "taskflow.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      labels:
        {{- include "taskflow.selectorLabels" . | nindent 8 }}
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - name: http
              containerPort: 3000
↑ Notice how the image tag, replicas, and names are all dynamic templates.

💻 Commands & Configuration

Creating and managing a chart:

bash 
# Create a new boilerplate chart
helm create taskflow-chart

# Check for syntax errors in your templates
helm lint ./taskflow-chart

# Render templates locally to see the generated YAML without deploying
helm template taskflow-release ./taskflow-chart --set image.tag=v1.0.0
↑ Useful commands for developing charts.

Deploying and managing releases:

bash 
# Install a chart
helm install taskflow ./taskflow-chart -f staging-values.yaml

# Upgrade an existing release
helm upgrade taskflow ./taskflow-chart --set image.tag=v1.2.0

# Idempotent install or upgrade (often used in CI/CD)
helm upgrade --install taskflow ./taskflow-chart -n production -f production-values.yaml

# View release history
helm history taskflow

# Rollback to revision 2
helm rollback taskflow 2

# Uninstall release
helm uninstall taskflow
↑ Managing the lifecycle of applications with Helm.

Working with Repositories:

bash 
# Add the Bitnami repository (great for DBs)
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update

# Search for a chart
helm search repo postgresql
↑ Accessing pre-built community charts.

⚠️ Common Mistakes

❌ Whitespace and Indentation Errors in YAML Rendering
✅ Fix: Use the | nindent 4 pipeline function in templates to correctly indent generated YAML blocks. Always test with helm template.
❌ Using helm install in CI pipelines
✅ Fix: helm install fails if the release already exists. Use helm upgrade --install in CI/CD to handle both initial deployment and future updates seamlessly.

🔧 Troubleshooting

  • Symptom: helm upgrade stuck in "pending-upgrade" state Cause: A previous upgrade failed or was interrupted, leaving a lock. Fix: Rollback the release or use helm rollback release-name. You can also try adding --force to upgrade.
  • Symptom: Values not being applied Cause: Value precedence issue. Fix: Remember precedence: --set overrides -f custom-values.yaml which overrides values.yaml. Ensure your value paths match exactly.

🏋️ Practice Exercise

Hands-On Exercise

Package Nginx with Helm

  1. Run helm create my-nginx.
  2. Edit my-nginx/values.yaml and change replicaCount to 2.
  3. Run helm template my-release ./my-nginx to verify it generates a Deployment with 2 replicas.
  4. Run helm install my-release ./my-nginx to deploy it to your cluster.
  5. Run helm upgrade my-release ./my-nginx --set replicaCount=3 to scale it.
  6. Run helm uninstall my-release to clean up.
