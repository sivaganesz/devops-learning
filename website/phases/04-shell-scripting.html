💡 What Is It?

A shell script is a text file containing a sequence of commands for a UNIX-based operating system. Bash (Bourne Again SHell) is the default and most widely used shell in Linux.

While modern DevOps uses tools like Ansible or Terraform for heavy lifting, at the lowest level, everything relies on Bash. Every job step in a GitLab CI/CD pipeline or GitHub Actions workflow is ultimately executed as a Bash script on a runner.

🎯 Why Do We Need It?

Before

A human logs into a server and types 15 different commands sequentially to backup a database, pull code, and restart services. If they make a typo on command #12, the system breaks.

After

A single automated script runs those 15 commands. It handles errors gracefully, can be reviewed via Pull Request, and executed exactly the same way across Development, Staging, and Production environments.

🧠 Mental Model

🧠 Mental Model

Think of a shell script like a recipe for a kitchen robot. You cannot just say "Bake a cake" (like you might with Terraform). You must provide the exact sequential instructions: "Get bowl. Add 2 eggs. Mix. If egg drops on floor, stop immediately and alert chef."

Trigger (CI/CD / Cron) → Bash Interpreter (/bin/bash) → Sequential Command Execution → Exit Code (0 or 1)

⚙️ How It Works

The Shebang

Every script starts with a shebang #!/bin/bash or #!/usr/bin/env bash. This tells the OS which interpreter to use when executing the file.

Variables & Special Variables

Variables do not have spaces around the equals sign: NAME="TaskFlow". Always double quote variables when using them: echo "$NAME" to prevent word splitting.

  • $0: The name of the script itself.
  • $1, $2, etc.: Positional arguments passed to the script.
  • $?: The exit code of the LAST executed command. (0 means success).

Exit Codes and Safety (Strict Mode)

By default, Bash will keep running even if a command fails! For DevOps, this is dangerous. We always add set -euo pipefail at the top of our scripts:

  • -e: Exit immediately if any command returns a non-zero exit status.
  • -u: Treat unset variables as an error and exit immediately.
  • -o pipefail: If any command in a pipeline fails (e.g., bad_cmd | grep foo), the whole pipeline fails, rather than just returning the exit code of the last command.

Conditionals & Loops

Use [[ ]] for conditionals instead of the older [ ], as it handles strings safely. Common flags: -z (string is empty), -f (file exists), -d (directory exists).

🔗 How This Applies to TaskFlow

TaskFlow Project

CI/CD Pipeline Jobs are Scripts

In our .gitlab-ci.yml file, the deployment job literally executes Bash commands on the runner. We will write a deployment verification script that polls the TaskFlow API /health endpoint to ensure the new deployment actually started successfully before marking the CI job as passed.

💻 Commands & Configuration

bash 
#!/usr/bin/env bash
set -euo pipefail # The DevOps standard

URL="http://localhost:3000/health"
MAX_RETRIES=5

echo "Starting health check for $URL"

for ((i=1; i<=MAX_RETRIES; i++)); do
    # curl -s (silent), -o /dev/null (discard output), -w "%{http_code}" (print status)
    STATUS=$(curl -s -o /dev/null -w "%{http_code}" "$URL" || echo "failed")
    
    if [[ "$STATUS" == "200" ]]; then
        echo "✅ Service is healthy!"
        exit 0
    fi
    
    echo "Attempt $i/$MAX_RETRIES: Status was $STATUS. Retrying in 2 seconds..."
    sleep 2
done

echo "❌ Service failed to become healthy."
exit 1
↑ A robust health-check polling script. This is how CI systems know a deployment finished.

⚠️ Common Mistakes

❌ Forgetting to quote variables
✅ Fix: Always use "$VAR". If $VAR contains spaces (e.g., "File name.txt") and you run rm $VAR, bash will try to delete two files: "File" and "name.txt". rm "$VAR" deletes the correct file.
❌ Not making the script executable
✅ Fix: You must run chmod +x script.sh before you can run it via ./script.sh.

🔧 Troubleshooting

  • Symptom: Script behaves weirdly or variables are blank, but no errors show up. Cause: The script is silently continuing on errors and unbound variables. Fix: Add set -euo pipefail at the top. Run with bash -x script.sh to see an execution trace line-by-line.

🏋️ Practice Exercise

Hands-On Exercise

Write an Environment Validator

  1. Create a script called check_env.sh and make it executable.
  2. Use a for loop to iterate over an array of required variable names (e.g., DB_HOST, DB_USER, DB_PASS).
  3. For each variable, check if it is set (using -z "${!VAR:-}").
  4. If any are missing, print an error and exit with code 1. If all exist, print "Ready" and exit 0.
  5. Test it by running ./check_env.sh and then DB_HOST=localhost DB_USER=admin DB_PASS=123 ./check_env.sh.

🧪 Knowledge Check

In UNIX, return values (stdout strings) are meant for data passing. The Exit Code is a standard OS-level signal. CI/CD pipelines (like GitLab or Jenkins) exclusively read the Exit Code (0 = pass, !=0 = fail) to determine if the pipeline job succeeded.
