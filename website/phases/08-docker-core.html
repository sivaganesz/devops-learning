Docker Core Concepts

Learn the foundational concepts of containerization. Understand how Docker solves the "it works on my machine" problem, how it differs from VMs, and the underlying Linux technologies that make it work.

💡 What Is It?

Docker is an open-source platform that automates the deployment, scaling, and management of applications inside lightweight, portable environments called containers.

Think of Docker as the shipping container of the software world. Before standard shipping containers, cargo was loaded individually—sacks, barrels, boxes—making loading and unloading slow, error-prone, and inconsistent across different ships and ports. Standardized containers revolutionized shipping by providing a uniform way to package any cargo.

Similarly, Docker standardizes how software is packaged. A Docker container packages the application code along with all its dependencies, libraries, and configuration files into a single artifact that runs reliably on any environment—whether it's a developer's laptop, a testing server, or a production cloud environment.

🎯 Why Do We Need It?

Before Docker

The "It works on my machine" problem. Developers had to write detailed setup documentation for environments. Applications often failed in production due to OS differences, missing system libraries, or conflicting dependency versions (e.g., App A needs Node.js 14, App B needs Node.js 18). Deployments were manual, slow, and fragile.

After Docker

Run anywhere reliably. The application and its exact environment are packaged together. If the container runs on the developer's laptop, it is guaranteed to run exactly the same way in production. Dependency conflicts disappear because each app is isolated in its own container.

🧠 Mental Model

🧠 Mental Model: The Container Factory

A Dockerfile is the blueprint. `docker build` takes the blueprint and creates an Image (a read-only mold). `docker run` uses that mold to stamp out a running Container (an active, isolated instance).

Dockerfile (Blueprint) → Image (Read-Only Layers) → Container (Running Process)

⚙️ How It Works

Virtual Machines vs Containers

It's crucial to understand why containers are not VMs. They operate on entirely different levels of abstraction.

Feature Virtual Machine (VM) Container (Docker)
Architecture Virtualizes the hardware via a Hypervisor. Virtualizes the OS. Shares the host kernel.
Size Gigabytes (includes full OS). Megabytes (only app + dependencies).
Boot Time Minutes (has to boot a full OS). Milliseconds (just starting a process).
Isolation High (hardware-level isolation). Medium (process-level isolation).

The Magic of Linux: Namespaces and cgroups

Containers are not magic; they are just Linux processes that have been isolated using kernel features:

  • Namespaces: Provide isolation. They trick a process into thinking it has its own isolated instance of global resources.
    • PID: Process IDs (container thinks it's PID 1).
    • NET: Network interfaces (container gets its own IP).
    • MNT: Mount points (container has its own filesystem).
    • UTS: Hostname.
    • USER: User privileges.
  • cgroups (Control Groups): Provide resource limitation. They ensure a container cannot consume more CPU, Memory, or I/O than it is allocated, preventing noisy neighbor problems.

Images and Layers

A Docker image is constructed from a stack of read-only layers. Every instruction in a Dockerfile (like `COPY` or `RUN`) creates a new layer. These layers are stacked using a Union Filesystem (like `overlay2`), where the top layer wins if files conflict.

When you start a container from an image, Docker adds a thin, writable "container layer" on top of the read-only image layers. Any changes made by the running container (writing files, modifying data) happen in this writable layer. If you delete the container, the writable layer is deleted, but the underlying image layers remain untouched.

Because layers are read-only, they can be safely shared across different images, saving massive amounts of disk space and download time.

🔗 How This Applies to TaskFlow

TaskFlow Project

Running the Application

In our TaskFlow project, the backend API is built using NestJS. Instead of forcing every developer to install Node.js 20, PostgreSQL, and configure them manually, we provide Docker images.

When you run docker run -p 3000:3000 taskflow-api:latest, Docker pulls the taskflow-api image (if not present locally), creates a container (allocating namespaces/cgroups), adds a writable layer, maps host port 3000 to container port 3000, and starts the Node.js process inside.

💻 Essential Commands

bash 
# Run a container (pulls image if needed, starts it, attaches terminal)
# -i = interactive, -t = tty, --rm = remove container when it exits
docker run -it --rm ubuntu:22.04 /bin/bash
↑ Starts an interactive Ubuntu shell, cleans up when you exit.
bash 
# Run a container in the background (detached) with port mapping
docker run -d -p 8080:80 nginx:alpine
↑ Runs Nginx in background, mapping port 8080 on your machine to 80 in container.
bash 
# List running containers
docker ps

# List all containers (including stopped ones)
docker ps -a
↑ View container status and IDs.
bash 
# View logs of a running container
docker logs -f <container_id>
↑ The -f flag follows the logs in real-time, like `tail -f`.
bash 
# Execute a command in an already running container
docker exec -it <container_id> sh
↑ Drop into a shell inside a running container to debug.

⚠️ Common Mistakes

❌ Treating containers like VMs

People often try to SSH into containers, install packages, and update code manually while it's running, treating it like a persistent server.

✅ Fix: Containers are ephemeral. Any changes made to a running container are lost when it's removed. If you need a permanent change, update the Dockerfile and build a new image.

🔧 Troubleshooting

  • Symptom: Container exits immediately after starting. Cause: The main process (PID 1) finished or crashed. A container only lives as long as its main process. Fix: docker logs <container_id> to see the error. Ensure the main command is long-running (not a background daemon).
  • Symptom: Host machine running out of disk space. Cause: Accumulation of unused images, stopped containers, and volumes. Fix: docker system prune -a to clean up unused resources.

🏋️ Practice Exercise

Hands-On Exercise

Explore Container Isolation

  1. Run an Alpine container interactively: docker run -it alpine sh
  2. Inside the container, create a file: touch /hello-world.txt
  3. Exit the container (type exit or Ctrl+D).
  4. Run a NEW Alpine container: docker run -it alpine sh
  5. Check for the file: ls /hello-world.txt. Notice it's not there!
  6. Exit and find your stopped containers using docker ps -a. Clean them up with docker rm <container_id>.
