Git & Git Workflows

Understand how Git really works under the hood and learn the workflows that power CI/CD pipelines.

⚠️ Prerequisites
  • Basic command line knowledge from Phase 03
✅ What You Will Learn
  • How Git stores snapshots (Commits, Trees, Blobs).
  • The Three Areas: Working Directory, Staging, Repository.
  • Branching, Merging, and Rebasing correctly.
  • Git workflows used in modern DevOps (Trunk-based development).

💡 What Is It?

Git is a distributed version control system. Unlike older systems that store file diffs (changes), Git thinks of its data as a stream of snapshots of a miniature filesystem. Every time you commit, Git takes a picture of what all your files look like at that moment.

In DevOps, Git is the source of truth. Git is where CI/CD pipelines start (GitOps). A push to a specific branch or a tag creation is what triggers automated testing, building, and deployment.

🎯 Why Do We Need It?

Before

Code is passed around in zip files. Folder names look like project-final-v2-real-final.zip. If two people edit the same file, changes are lost. Deployments happen manually via FTP.

After

Every change is tracked with a cryptographic hash, author, and timestamp. Multiple developers work concurrently on branches, merge safely, and changes automatically trigger CI/CD pipelines for deployment.

🧠 Mental Model

🧠 Mental Model

Think of Git as three rooms. The Working Directory is your messy desk where you work. The Staging Area is a box where you pack things you want to ship. The Repository is the secure vault where packed boxes are permanently stored with a serial number.

Working Dir (Modified) git add → Staging Area (Indexed) git commit → Repository (.git)

⚙️ How It Works

Commits, Trees, and Blobs

Inside the hidden .git/objects directory, Git stores three main types of objects:

  • Blobs: The actual file contents.
  • Trees: Directories. A tree points to blobs and other trees.
  • Commits: A snapshot pointer. A commit points to the top-level Tree, contains metadata (author, message), and points to parent commits.

Branches are just Pointers

A branch in Git isn't a copy of your files; it's simply a lightweight, movable pointer to a specific commit. The special pointer HEAD tells Git which branch you are currently on. Creating a branch is instantaneous because it just creates a 41-byte file containing a commit hash.

Merge vs Rebase

Merge takes two diverged branches and ties them together with a new "merge commit". It preserves history exactly as it happened. Rebase takes your branch's commits and replays them on top of another branch. It creates a clean, linear history but rewrites commit hashes.

⚠️
Golden Rule of Rebasing

Never rebase commits that exist outside your repository and that people may have based work on (like public/shared branches).

  • You branch off main to feat/add-login.
  • You push and open a Merge Request (MR).

💻 Commands & Configuration

bash 
# Create and switch to a new branch
git switch -c feature/new-api
↑ Replaces the older `git checkout -b`. Creates the branch and moves HEAD to it.
bash 
# See a clean visual history of branches and commits
git log --oneline --graph --all
↑ Highly recommended alias. Shows how branches diverge and merge visually in the terminal.
bash 
# Create an annotated tag for a release
git tag -a v1.0.0 -m "Initial Release"
git push origin v1.0.0
↑ Annotated tags include author info and dates. Pushing tags requires explicit specification.

⚠️ Common Mistakes

❌ Mistake: Committing Secrets (API Keys, Passwords)
✅ Fix: Never commit .env files. If you do, the secret is permanently in Git history even if you delete the file later. You must use tools like BFG Repo-Cleaner or git filter-branch to rewrite history to remove it.

🔧 Troubleshooting

  • Symptom: "Updates were rejected because the tip of your current branch is behind" Cause: Someone else pushed to the remote branch since you last pulled. Fix: Run git pull --rebase to apply their changes, then replay yours on top, then git push.
  • Symptom: Accidentally committed to the wrong branch Cause: Forgot to create/switch branches before committing. Fix: git reset HEAD~1 --soft (undoes commit but keeps changes in staging), then switch to right branch, then commit.

🏋️ Practice Exercise

Hands-On Exercise

Simulate a Pull Request Workflow

  1. Initialize a local repo: git init demo and cd demo.
  2. Create an initial commit: echo "v1" > file.txt && git add . && git commit -m "init"
  3. Create a branch: git switch -c feature/a. Modify file.txt, add and commit.
  4. Switch back to main: git switch main. Notice file.txt reverts to "v1".
  5. Merge the branch: git merge feature/a. This will be a fast-forward merge.
