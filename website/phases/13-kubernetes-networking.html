Kubernetes Networking

Understand Services, CoreDNS, Ingress Controllers, and Network Policies to connect and secure your Pods.

💡 What Is It?

Kubernetes networking is the system that allows all components inside and outside the cluster to communicate. Since Pods are ephemeral and constantly destroyed/recreated, relying on their IP addresses is impossible. K8s introduces abstractions like Services and Ingress to provide stable routing.

🎯 Why Do We Need It?

Before

You deployed 3 backend Pods. A frontend wants to talk to them. You try to hardcode their IP addresses. When a Pod dies and gets rescheduled, it gets a new IP, breaking your frontend connection.

After

You place a K8s Service in front of the backend Pods. The Service gets a stable, unchanging IP and DNS name. The frontend talks to `backend-service`, which load-balances seamlessly to the current healthy Pods.

🧠 Mental Model

🧠 Mental Model

Think of an Ingress as a hotel receptionist who checks your destination and routes you to the right floor (Service). The Service is the floor manager, directing you to an available open room (Pod).

User → Ingress → Service → Endpoints → Pod

⚙️ How It Works

A Service gets a stable IP (ClusterIP). It uses label selectors to find target Pods and updates a corresponding Endpoints object. `kube-proxy` writes iptables rules on every node to intercept traffic to the ClusterIP and forward it to a Pod.

CoreDNS runs inside the cluster and maps Service names to their ClusterIPs. Format: `<svc-name>.<namespace>.svc.cluster.local`.

Ingress provides a single entry point (usually port 80/443) that inspects HTTP host headers or paths to route traffic to various internal Services.

🔗 How This Applies to TaskFlow

TaskFlow Project

Our Running Example

For TaskFlow: The PostgreSQL database has a `ClusterIP` Service because only internal apps need it. The NestJS backend has a `ClusterIP` Service. We use an `Ingress` resource configured with an Nginx Controller to accept external traffic on `api.taskflow.com` and route it to the backend Service. We also enforce a Network Policy so ONLY the backend pods can communicate with the PostgreSQL pods.

💻 Commands & Configuration

yaml 
# service.yaml
apiVersion: v1
kind: Service
metadata:
  name: taskflow-backend-svc
spec:
  type: ClusterIP
  selector:
    app: taskflow-backend
  ports:
    - port: 80
      targetPort: 3000
↑ Maps cluster-internal port 80 to container port 3000 on Pods matching `app: taskflow-backend`.
yaml 
# ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: taskflow-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  rules:
  - host: api.taskflow.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: taskflow-backend-svc
            port:
              number: 80
↑ Routes external traffic from api.taskflow.com to the backend service.

⚠️ Common Mistakes

❌ Using a LoadBalancer Service for everything
✅ Fix: This is expensive as it provisions a new cloud LB for every service. Use an Ingress Controller (one LoadBalancer) and route traffic via Ingress resources.

🔧 Troubleshooting

  • Symptom: Service is not routing traffic to Pods Cause: Service selector labels do not match the Pod labels. Fix: Check `kubectl get endpoints `. If empty, fix the labels.
  • Symptom: Ingress returns 502 Bad Gateway Cause: The backend Service is reachable but the Pod application isn't running or listening on the wrong port. Fix: Verify container port matches `targetPort` and application is ready.

Hands-On Exercise

Exposing an app locally

  1. Deploy the nginx deployment from Phase 12.
  2. Run `kubectl expose deployment nginx-deployment --type=NodePort --port=80`.
  3. Run `kubectl get svc nginx-deployment` and note the mapped 30000+ port.
  4. Access it via `minikube ip` or `localhost` and that port in your browser.

🧪 Knowledge Check

Ingress consolidates your routing rules behind a single cloud Load Balancer and external IP, which significantly reduces cloud costs and provides a unified entry point for TLS termination and path-based routing.
